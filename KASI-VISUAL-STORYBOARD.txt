  MOTION SPEC — ⟨fps⟩ loop, not a CSS transition:

     prog += (cap − prog) * 0.07          exponential approach, ~14 frames
                                          to close 63% of the remaining gap
     cap  =  90   while (!window.load || elapsed <= 650 ms)
             100  once BOTH conditions true

  So the bar visibly STALLS at 90% waiting for the load event. That stall is
  intentional — it reads as "charging the last cells". The moment cap flips to
  100 the bar snaps the last 10% in ~30 frames, prog is force-clamped to 100
  when it exceeds 99.3, the label swaps to "Full charge", and .done is added:

     #preloader.done  →  opacity 0 + visibility hidden, .7s ease

  ★ The label text change and the fade happen in the SAME frame. There is no
    beat where you read "Full charge" at full opacity. If you want that beat,
    you need a setTimeout before addClass('done').

  ── 3a. THE IDLE SPIN ──────────────────────────────────────────────────────

  Runs only while  (!dragging && p < 0.04):

        qYaw  = quaternion(axis = worldY, angle = dt * 0.4)
        qFree = qYaw ⊗ qFree            ← PREmultiply: world-space Y, not local

  0.4 rad/s ≈ one full revolution every 15.7 seconds. Slow enough to read as
  "displayed", not "spinning".

  ── 3b. DRAG-TO-TUMBLE ─────────────────────────────────────────────────────

  Guard:  onDown() returns immediately if p > 0.05.  Once you have scrolled
  past 5%, the car is on rails and drag is dead. ★

        pointerdown → canvas.setPointerCapture, cursor:grab → grabbing
        pointermove → qFree = Rx(dy*0.006) ⊗ Ry(dx*0.008) ⊗ qFree

  Both premultiplied, so tumbling is in WORLD axes — the car does not develop
  a local gimbal. Horizontal drag is 1.33× more sensitive than vertical.
  There is NO inertia and NO damping on release. The car stops the instant
  your finger stops. (The auto-spin resumes only if p is still < 0.04.)

           drag right ──►          drag down
              ⟳ +Y                    ⟳ +X
            ___                      ___
       ,---'   `---.  ⟳         ,---'   `---.
      [   ▄▄▄▄▄▄   ]  →        [   ▄▄▄▄▄▄   ]  ↓ nose dips toward viewer
       `---.___.---'            `---.___.---'

  ── 3c. THE ASCII "REVEALER FLASHLIGHT"  ★ signature effect ────────────────

  Desktop only — gated on matchMedia('(pointer:fine)'). A soft circle that
  follows the cursor converts ONLY THE CAR into monospace glyphs. Background
  is never converted. It is a genuine two-pass post-process:

    PASS 1                          PASS 2 (fullscreen quad + ShaderMaterial)
    ┌───────────────┐               ┌────────────────────────────────────┐
    │ hScene.bg=null│  heroRT       │ frag:                              │
    │ clear α=0     │ ─────────────►│  normal  = mix(u_bg, hi.rgb, hi.a) │
    │ render car    │  RGBA texture │  cell    = texture(scene,cellCentre)│
    └───────────────┘  α = car mask │  b       = luma(cell.rgb)          │
                                    │  idx     = floor((1−b) * 29)       │
                                    │  glyph   = atlas[idx][local uv]    │
                                    │  ascii   = mix(white, cell*0.62,   │
                                    │                 glyph)             │
                                    │  ring    = 1 − smoothstep(         │
                                    │              r−feather, r, dist)   │
                                    │  out     = mix(normal, ascii,      │
                                    │                ring * cell.a)      │
                                    └────────────────────────────────────┘

  Glyph atlas: a 29-character density ramp baked to a horizontal canvas strip,
  48px per cell, IBM Plex Mono 700:

        Ñ @ # W $ 9 8 7 6 5 4 3 2 1 0 ? ! a b c ; : + = - , . _ ␠
        └── dark / dense ──────────────────────────► light / sparse ──┘

    ★ The atlas is REBAKED once document.fonts.ready resolves, then
      atlasTex.needsUpdate = true. Before that it renders in the fallback
      monospace — a visible 1-frame glyph-shape pop on cold load.

  The flashlight geometry:

        cell size   = 10 * devicePixelRatio   (screen px per glyph)
        radius      → 0.18 * min(bufferW, bufferH)  on pointermove
        feather     = 0.45 * radius            (soft falloff band)
        mouse lerp  = 0.35/frame   (cursor trails slightly — deliberate lag)
        radius lerp = 0.15/frame   (grows/shrinks over ~15 frames)

  Sleep gate — the effect fades out as you scroll and then short-circuits:

        gate = 1 − clamp01(scrollY / (innerHeight * 0.25))
        if (radius < 0.5)  →  plain renderer.render(hScene, hCam); return;

  So by 25% of one viewport scrolled, the post-process is completely bypassed
  and you are paying zero cost for it. Radius also drops to 0 on
  document mouseleave and window blur.

  │  4.  THE SCROLL TIMELINE — master diagram                                │
  └──────────────────────────────────────────────────────────────────────────┘

  ONE normalised value drives everything:

        pTarget = clamp01( scrollY / (scrollHeight − innerHeight) )   ⟨scroll⟩
        p      += (pTarget − p) * (1 − exp(−dt * 7))                  ⟨fps⟩

  ★ This double-buffering is the entire reason the page feels "buttery".
    A mouse wheel delivers scroll in coarse 100px notches; pTarget jumps,
    but p glides. Time-constant is 1/7 s ≈ 143 ms to 63%. Frame-rate
    independent (uses exp(−dt·k), not a fixed lerp).

  Segment interpolation, ⟨fps⟩:

        find i such that KEYS[i].at ≤ p < KEYS[i+1].at
        t = smoothstep( (p − a.at) / (b.at − a.at) )      t² (3 − 2t)
        camPos = lerp(a.camV, b.camV, t)
        lookAt = lerp(a.lookV, b.lookV, t)
        bg     = a.colC.lerp(b.colC, t)          ← scene background, not CSS
        qCar   = (i===0) ? qFree.slerp(b.q, t)   ← blends OUT of the live spin
                         : a.q.slerp(b.q, t)

  ★ The i===0 branch is why the arrival spin doesn't snap. Whatever random
    orientation the car happens to be in when you start scrolling, it SLERPs
    from there into the fixed K1 pose. Every page-load has a different first
    3 metres of animation. That is a feature.

  ── 4a. THE "side" TRICK — how the car dodges the text ─────────────────────

  `side` is a screen-space lateral aim offset expressed as a fraction of the
  camera→target distance. It is applied AFTER the lookAt lerp:

        dir   = normalize(lookAt − camPos);   dist = |lookAt − camPos|
        right = normalize(dir × worldY)
        lookAt += right * (side * dist)

  Aiming the camera RIGHT pushes the subject to screen-LEFT, and vice-versa:

     side = −0.28                        side = +0.28
     ┌──────────────────────┐            ┌──────────────────────┐
     │ 01 — THE NAME        │            │       03 — PROVEN IN │
     │ KASI /ˈka·si/    ___ │            │ ___      DATA        │
     │ South African,  [CAR]│            │[CAR]     Every lap   │
     │ from lokasie…    ‾‾‾ │            │ ‾‾‾      is telemetry│
     └──────────────────────┘            └──────────────────────┘
       text LEFT, car RIGHT                car LEFT, text RIGHT
       (.chapter[data-align=left])         (.chapter[data-align=right])

  ★ On ≤720px, sideMul = 0 — the offset is disabled entirely and the camera
    additionally pulls back 12% (camPos = lookAt + (camPos−lookAt)*1.12) with
    FOV 54 instead of 38. Portrait would otherwise crop the car in half.

  ── 10c. THE DRIFT MODEL — what the player feels ───────────────────────────

  Velocity is a free 2-D vector; heading is a SEPARATE scalar. Tyres pull
  lateral slip toward zero, but the force is CLAMPED at a grip limit. Exceed
  it and the rear steps out.

        latAcc = clamp(−latSpeed * latStiff, −grip, +grip)
                                    (11)

        grip =  100   normal tarmac        ← huge; car is glued
                 30   two wheels on sand
                 16   handbrake (Space)    ← 6× less than tarmac

                      GRIP-LIMITED                 SLIP-LIMITED
                      (normal cornering)           (DRIFT)
         lateral   ▲                            ▲
         restoring │      ╱                     │    ┌──────── clamp at ±grip
         force     │    ╱                       │   ╱
                   │  ╱  slope = latStiff       │  ╱
                   │╱                           │╱
                   └────────────► latSpeed      └────────────► latSpeed
                                                    ↑ beyond here the tyre
                                                      cannot hold the car

    DRIFT FLAG:   |latSpeed| > 7 && speed > 10       (lateral slide)
               ||  handbrake && speed > 8            (deliberate)

    Two feedback loops make it controllable rather than random:

      (1) driftBoost — once |latSpeed| > 7, steering authority × 1.35.
          You get MORE counter-steer exactly when you need it.
      (2) self-align — above 4 m/s, the heading is pulled toward the actual
          velocity vector, scaled by grip/100:

              omega += slip * 0.9 * dt * (grip / CFG.grip)

          On tarmac (grip 100) that's a strong snap-back: the car straightens
          itself out of a slide. On the handbrake (grip 16) it's 6× weaker —
          the slide HOLDS. That single scale factor is the entire feel of the
          handbrake. ★

    Steering authority also scales with speed, then decays at high speed:

        speedFac = clamp(|fwdSpeed| / 12, 0, 1) / (1 + |fwdSpeed| * 0.010)

              1.0 ┤        ╭─╮
                  │       ╱   ╰──╮
              0.5 ┤      ╱        ╰────╮____
                  │     ╱                   ╰────
              0.0 ┼────╯
                  0    12       50        100  m/s
                  ↑ no steering  ↑ peak    ↑ high-speed stability

  ★ SIGN CONVENTION LANDMINE: steer = (left ? 1 : 0) − (right ? 1 : 0).
    Pressing LEFT INCREASES heading. Behind the chase cam that turns the car
    screen-left, which is correct. But it is inverted from the usual
    "right-hand rule" reading, and the autopilot code carries an explicit
    comment about it. Do not "fix" this sign without also flipping autopilot().

  ── 10e. CHASE CAMERA ─────────────────────────────────────────────────────

        zoom  = 1 + min(1, speed/80) * 0.30        ← pulls BACK when fast
        target = carPos − fwd * 30 * zoom,  y = 14 * zoom
        a      = 1 − 0.001 ^ (dt * 3.2 / 3)        ← frame-rate-independent
        camera.position.lerp(target, a)

        lookTarget.lerp(carPos + fwd*8  at y=2,  a * 1.6)
        camera.lookAt(lookTarget)

    Two separate lags, and the aim lag is 1.6× FASTER than the position lag.
    That difference is what produces the "the camera is chasing you" feel:
    the body of the shot trails, the aim catches up.

    The aim point is 8 units AHEAD of the car, not at the car. You are always
    looking slightly into the corner you're entering.

                   camera                     car        look point
                     ⊕ ─────── 30·zoom ───────► ▮ ──8──► ✛
                   y=14·zoom                   y=0       y=2
                     │                          │
                     └── lerps at a ────────────┴── lerps at a*1.6

  ★ At 80 km/h+ the camera is 39 units back and 18.2 up. The perceived speed
    increase comes from the widening frame, not from any FOV change — FOV is
    a fixed 38°.

        0        0.5       1.0       1.5       2.0       2.5      3.0s

    250 ms between stats — slow enough that you READ each one. The buttons

    ★ The delays are hard-coded as :nth-child(1..8). Add a ninth stat and it

      nth-child list when you add stats.

  │ 13.  RETURN TO MENU — the reverse transition                             │
  └──────────────────────────────────────────────────────────────────────────┘

        toMenu(scrollToEnd = true):
          state = 'menu';  hud/pause/results/countdown all display:none
          body.playing removed   → #story, rails, toggles, grain, title
                                   ALL reappear at once; scroll unlocks
          body.ended   removed
          Hero.show(true):
              #landing .fade and .gone removed  → opacity transitions 0→1
              active = true;  heroPhaseActive = true
                                 → the GAME LOOP short-circuits again
                                   (the race scene stops rendering entirely)
              body.hero-phase added  → .tilt + #hud hidden
              scrollTo(0, scrollMax())    ← JUMPS TO THE BOTTOM
              onScroll()                  → pTarget = 1.0
          #bestLine = "SESSION BEST — MM:SS.mmm"
          reset()

  ★ scrollToEnd = true is the key UX decision. You do NOT get dumped back at
    the top of a seven-screen brand story after every race. You land exactly
    where you left — CH5, car on the grid, START ENGINE lit — one click from
    racing again. The only path that uses scrollToEnd = false is the very
    first toMenu(false) call at boot, which puts you at the top for the
    arrival frame.

  ★ p does NOT jump — pTarget jumps to 1.0 and p eases toward it at the usual
    1/7s time constant. So the hero camera glides into the K6 pose over ~400ms
    while #landing fades back in over 800ms. The two overlap, which is what
    makes the return feel like a pull-back rather than a cut.

  │ 16.  FRAME BUDGET — who renders what, when                               │
  └──────────────────────────────────────────────────────────────────────────┘

  TWO independent requestAnimationFrame loops run for the entire life of the
  page. Each is gated so that exactly one does real work at any moment:

    Hero.frame()                     Game.loop()
    ┌──────────────────────┐         ┌──────────────────────┐
    │ if (!active) return; │         │ if (heroPhaseActive) │
    │                      │         │      return;         │
    │ ease p               │         │                      │
    │ interpolate keyframe │         │ countdown / physics  │
    │ set car quaternion   │         │ AI, particles, crowd │
    │ revealEnv            │         │ HUD writes, minimap  │
    │ rail % + title α     │         │ camera lerp          │
    │ renderHero()  ───────┼─────┐   │ render(scene,camera) │
    │   [ASCII 2-pass or   │     │   └──────────┬───────────┘
    │    plain render]     │     │              │
    └──────────────────────┘     ▼              ▼
                            ONE WebGLRenderer, ONE canvas, ONE GL context

  Cost characteristics worth knowing:

    Hero phase, cursor moving, top of page   2 draws (RT + fullscreen quad)
    Hero phase, scrolled > 25% viewport      1 draw  (post-process bypassed)
    Race                                     1 draw + a 150×150 canvas2d blit
                                             + ~12 DOM text writes per frame

  ★ THE DOM WRITE COST: the race loop writes textContent to timer, speed,
    driftScore, battPct, battKwh, lapVal and style.width to progFill and
    battFill EVERY FRAME. That is 8+ style/layout touches at 60Hz. Only
    #posTag is change-guarded. If you ever profile a jank spike on a low-end
    phone, start here — everything except the timer could be throttled to
    10Hz with zero perceptible difference.

  ★ Minimap.draw() clears and re-blits a cached 150×150 offscreen canvas plus
    8 arcs every frame. Also a candidate for throttling.

  ★ InstancedMesh is used for every repeated species (dunes, palms, acacias,
    rocks, huts, flamingos, posts, dashes, crowd bodies, crowd heads) —
    which is why a scene with hundreds of objects is a handful of draw calls.
    Only the crowd's instanceMatrix is updated per-frame; everything else is
    written once at construction.

  ★ Scenery layout is deterministic (LCG seeded 20260706). Screenshots and
    bug reports are reproducible. Do not replace rnd() with Math.random().

   THE ONE-PARAGRAPH VERSION, for whoever inherits this:

   A cream preloader charges a KASI wordmark like a battery, then dissolves
   onto a white void holding a single gradient-liveried F1 car that spins
   slowly and turns into ASCII glyphs wherever your cursor hovers. Scrolling
   does not move the page past the car — it moves a CAMERA around it, along a
   seven-keyframe orbit, while five chapters of brand copy slide in from the
   opposite side of the screen and the 3-D background lerps through the
   active colour scheme. A vertical rail on the right reads your scroll
   position as state-of-charge. At the bottom of the scroll a sand ground and
   a chequered start line fade in underneath the car, the camera settles into
   the exact pose the game's chase camera uses, and START ENGINE lights up
   directly beneath the car. Clicking it dissolves the white stage off a
   fully-built Rift Valley circuit — flamingos, dunes, acacias, a jumping
   crowd — counts you down, and hands you a drift model whose entire
   character lives in one grip constant. One lap later the car keeps driving
   itself while four cinematic camera shots cycle behind a half-transparent
   panel that slides your telemetry in, one number every 250 ms. MENU puts
   you back at the bottom of the scroll, one click from doing it again.

   Every screen is one HTML file. Every colour is a CSS custom property whose
   VALUE is swapped at runtime. Every repeated object is an InstancedMesh.
   Every random placement is seeded. Nothing here is an accident.
